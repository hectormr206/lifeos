# Golden Sets

Labeled evaluation sets for LifeOS/Axi model benchmarking. All files are JSONL;
lines starting with `//` or `#` are comments (every loader skips them). All
natural-language content is Spanish (Axi's production language) except code
snippets, which stay in their source language.

| File | Cases | Consumed by | Purpose |
| --- | --- | --- | --- |

| `extraction_quality.jsonl` | 69 | `lifeos.agents.eval.scoring.score_extraction` (extraction role) | Nano entity-extraction: per-field accuracy + case pass rate. |

Schema: `{id, domain, today, records_block, question, expected: {must_contain: [[alternatives...]], must_not_contain_numbers_absent_from_records, refusal_expected?}}`. Deterministic scoring: any-of `must_contain` groups + fabricated-number detector (any number token in the reply absent from records_block+question fails; integers 0-10 and question-mentioned years tolerated). Schema: `{id, facts_text, constraints: {min_sentences, max_sentences}, rubric}`. Metrics: `{n, numeric_fidelity_rate, structure_rate, judge_score?, note?, failed_ids}`. |

Schema: `{id, kind: meeting_window|executive|chat_archive, transcript, planted_atoms: [{label, must_contain_any}], required_sections? (executive only)}`. | `structured_parsing.jsonl` | 14 | `model_audit.py` parsejson role | Strict JSON/label parsing fallbacks across 5 production contracts: `when` (`reminder_brain.parse_when_brain` → `{"when_iso": ...|null}`), `schedule` (`reminder_brain.parse_reminder_brain` scheduling-intent JSON), `voice_intent` (`intents._brain_classify` fixed-label set), `graph_facts` (`extractor.extract_and_store` → `{"facts": [...], "relations": [...]}`), `coreference` (`identity._llm_same_entity` → si/no). Schema: `{id, kind, system?, prompt, max_tokens, negative?, expected}`. Metrics: `{n, pass_rate, negative_pass_rate, json_valid_rate, failed_ids}`. |
| `agentic_research.jsonl` | 12 | `model_audit.py` agentic role | Multi-round agentic research reproducing `axi.briefing.run_agentic_briefing` EXACTLY: the harness sends the production system prompt (`briefing.build_briefing_system(today)` + `brain._ask_with_tools_impl`'s Spanish tool-instructions suffix, imported not paraphrased), offers the production `axi.web_tools` schemas (`web_search` with `time_range`/`categories` + `web_fetch`), executes CANNED handlers returning the production JSON shapes (`{ok, query, results}` / `{ok, url, text, links}`) fed back as `role=tool` messages (`tool_call_id` + `name`, `brain._run_tool_call` shape), pins production sampling (temp 0.7 / top_p 0.8 / top_k 20, `max_tokens=4096` — what the prod tool loop sends to ANY serving model), caps at 5 tool rounds, then drops the tools and forces synthesis with the verbatim `_FINAL_SYNTHESIS_PROMPT`. Case variety: search-only, fetch-only, parallel search+fetch, chained search→fetch, multi-topic (2 searches), reformulated retry (keyed canned queries — the first query returns `ok=false` empty), distractor selection (search + fetch variants), links citation, one tool-optional case. Schema: `{id, prompt (ES briefing task), canned_tools: {web_search: {query_must_mention, results \| queries: [{match_any, results}] + default_results}, web_fetch: {url: page_text \| {text, links}}}, expected: {must_call_tools, tools_required? Semantics: `tool_correct_rate` = share of cases whose tool discipline held (every `must_call_tools` tool called AND every `query_must_mention` term present in at least one issued query; `tools_required: false` cases count as satisfied by definition, so skipping tools is never punished where allowed); `mean_rounds` = average TOOL rounds used (one round = one model reply containing tool_calls; 0 = answered without tools, 5 = exhausted the cap and was forced to synthesize with tools dropped). |

| `tool_stress.jsonl` | 10 | `model_audit.py` toolstress role | MCP-style tool-protocol robustness: can the model use a crowded tool registry (and a skill-like procedure doc) correctly? Every case runs a REAL multi-round loop (≤ 6 tool rounds, then forced wrap-up with tools dropped) offering ALL ~13 deliberately confusable tools in `model_audit.TOOLSTRESS_REGISTRY` (`create_reminder`/`create_calendar_event`/`create_task`, `search_web`/`search_memory`/`search_files`, `get_health_summary`/`get_health_entries`, `send_notification`/`send_message`, `update_config` with nested `changes`, `export_data` with nested `filters.date_range`, `create_expense`), with canned handlers returning per-case JSON. 4 case kinds: `selection` (exactly ONE tool is right, 2-3 registry neighbours are plausible-but-wrong and FORBIDDEN; args scored by containment on dotted paths), `nested_args` (deep nested args with enums + ISO dates scored EXACTLY on dotted paths), `error_recovery` (the canned handler returns an error JSON on the FIRST call — the model must retry the SAME tool with the named arg corrected and acknowledge success), `procedure` (a skill-like PROCEDIMIENTO in the system prompt: steps must appear in the call log as an ORDERED subsequence with values threaded from canned step results, e.g. a `person_id` returned by step 1 reused in step 2). ## Conventions

- **Any-of groups**: where a schema uses `must_contain: [[...], [...]]`, the outer
  list is AND, the inner list is OR. Matching is lowercase and accent-stripped.
- **No-call / clean trap cases** exist in `tool_calling.jsonl` and
  `code_review.jsonl` so over-eager models pay for hallucinated calls/bugs.
- Sets are versioned by their header comment; append cases rather than mutating
  existing ids so historical registry rows stay comparable.
